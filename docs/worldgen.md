# World generation

How Noita builds a world: the two phases, the ordered steps, the data files involved, and
where each knob lives.

World generation in Noita is **not** one algorithm. It is a colour-indexed map, a set of
per-biome generators chosen by a three-valued type tag, a material-selection pass that runs
once per pixel, and a pile of Lua hooks. Nothing about it is exposed as a "worldgen settings"
screen, because there is no single struct of settings: the parameters live in ~150 XML
attributes spread over five different element types, plus a handful of `magic_numbers.xml` entries.

- [worldgen-biomes.md](worldgen-biomes.md) - the biome data model: the colour map, the
  `Biome` record, all 87 fields with their compiled-in defaults, and `BiomeModifiers`.
- [worldgen-terrain.md](worldgen-terrain.md) - how one pixel becomes one material: the
  three topology types, the cave noise, and the exact ore-placement algorithm.
- [worldgen-wang.md](worldgen-wang.md) - wang tiles: the template format, the herringbone
  rule, the four planes, and the colour-to-Lua-function table.
- [worldgen-pixelscenes.md](worldgen-pixelscenes.md) - pixel scenes, backgrounds, vegetation,
  decor and pixel sprites: what gets placed, when, and where.
- [worldgen-reference.md](worldgen-reference.md) - every default value, every offset, in one
  table per struct.

Addresses are for one Steam build of the 32-bit `noita.exe` and will move on update. Function
*behaviour* is stable; treat every address as a pointer into one build.

## The shape of the world

| quantity | value | where it comes from |
|---|---|---|
| chunk | 512 x 512 **cells**, 1 cell = 1 pixel | hardcoded `0x200` at `0x0073c220` |
| world | 70 x 48 chunks | `BiomeMapSetSize( 70, 48 )` in `data/scripts/biome_map.lua` |
| world extent | x in [-17920, +17920) px, y in [-7168, +17408) px | the lookup adds 35 x 512 = 17920 to x and `biome_offset_y` x 512 = 7168 to y before indexing the biome map |
| cell storage | **two** 1 MiB blocks per chunk, both 262144 x 4 bytes: one array of cell pointers, one flat `uint32` material array | `0x0073c220`, `0x0073b040` |
| seed | one `int32`, `0x01205004`, set by `SetWorldSeed` | `0x007c3d90` |

Two different index schemes are in play.
For **biome** lookup the in-chunk pixel index is `coord & 0x1FF` and the chunk index is
`coord >> 9`, whose X is wrapped by `% chunks_wide` and whose Y is clamped - there is no torus
on the biome array. For the **cell-chunk** array the expression is
`((coord >> 9) - 0x100) & 0x1FF`, which *is* a 512-chunk torus, biased by -256. The torus is
roughly seven times further out than the biome window in x (256 chunks against 35), so it never shows up in play, but it is what a distant
teleport eventually wraps onto.

## The biome map is a PNG, and it is generated by Lua

The map is a 70 x 48 image, `data/biome_impl/biome_map.png`, and **one pixel of it is one
chunk of the world**. It is not read directly from the PNG at load; `magic_numbers.xml` sets

```xml
BIOME_MAP="data/scripts/biome_map.lua"
```

and that script is executed:

```lua
BiomeMapSetSize( 70, 48 )
BiomeMapLoadImage( 0, 0, "data/biome_impl/biome_map.png" )
```

which is why mods can replace the map without touching the executable - and why
`BiomeMapGetSize()` documents that it "returns that context, if BIOME_MAP in magic_numbers.xml
points to a lua file". `BiomeMapLoad`, `BiomeMapLoad_KeepPlayer`, `BiomeMapLoadImage`,
`BiomeMapLoadImageCropped`, `BiomeMapSetPixel`, `BiomeMapGetPixel` and `BiomeMapSetSize` are
all reachable from Lua; `BiomeMapLoad` is marked deprecated in its own signature.

Each map pixel is an **RGBA colour**, and `data/biome/_biomes_all.xml` is the lookup table from
colour to biome:

```xml
<BiomesToLoad biome_image_map="data/biome_impl/biome_map.png" biome_offset_y="14">
  <!-- index is between 0 and 10 -->
  <Biome biome_filename="data/biome/hills.xml" height_index="0" color="ff36d517"/>
  <Biome biome_filename="data/biome/hills.xml" height_index="0" color="ff3d3e40"/>
  ...
```

`biome_offset_y` is an integer on the `BiomesToLoad` element. The loader multiplies it by 512 and
stores it as the world's Y origin (14 x 512 = 7168 px), and every biome lookup adds that origin to
the pixel's Y before taking the chunk row - so map row 14 is the row containing y = 0. The X origin
is half the map width in pixels (35 x 512). `height_index` is an integer on each `<Biome>` entry
that the shipped file documents as "index is between 0 and 10"; its use is not recovered - it is
not the biome id (that is the colour). A pixel whose colour is not in the
table produces `"Biome load error - couldn't find biome for color: "` and the pixel stays empty -
which is why "Biome - couldn't find a biome at: " appears in the log if you edit the map without
editing the table.

There are several map variants shipped as data: `biome_map_demo.png`, `biome_map_niilo.png`,
`biome_map_boss.png`, `biome_map_crypt.png`, `biome_map_lab.png`, `biome_map_metagame.png`,
`biome_map_trailer.png`, `biome_map_the_end.png`, and `biome_map_newgame_plus.lua`/`.png`.

## Phase 1: load time, once per world

Everything here happens inside `GameWorld::Load_Threaded` before the first frame. The entry
point is **`0x0087a900`**, and its own log lines bracket it:

```
ProceduralTerrain::Init(  ...  ProceduralTerrain - worldseed: <n>
Generating world...  ...  World generation took:  ...  ProceduralTerrain::Init took:  ...
```

In order:

1. **Read the biome list.** `BiomesToLoad` from `_biomes_all.xml` gives the colour table, the
   map path and `biome_offset_y`.
2. **Run the map script.** If `BIOME_MAP` names a `.lua` file, a `BiomeMapLuaManager` is created
   and the file is executed; the manager also gets an `OnBiomeConfigLoaded` callback and a
   `biome_modifiers_inject_spawns` hook, which is the supported way for a mod to change biome
   definitions before they are used.
3. **Load every biome file** (`0x0086b9f0`, `source/procedural_utils/biome.cpp`). Each
   `data/biome/NAME.xml` has exactly two children, `<Topology>` and `<Materials>`, and a file
   that lacks either is rejected with
   `"Error - Couldn't load biome: <file> - it lacked Topology or Materials (or the file doesn't exist)"`.
   The loader also builds the **colour -> biome id map** (`malloc(W*H*4)`) and an 8-byte-per-pixel
   secondary map.
4. **Load the template and the biome script into a wang map** (`0x00867de0`,
   `"wang: <name> - couldn't load scripts"`). It expands the `wang_template_file` into a
   `wang_map_width` x `wang_map_height` image and attaches the biome's own `lua_script` as the
   colour dispatcher. Despite the log wording it does not read `data/scripts/wang_scripts.csv`;
   that file is read by two other functions (`0x006e9f30`, `0x006afaa0`).
5. **Build each biome's cave / wang map** (section D of
   [worldgen-terrain.md](worldgen-terrain.md)). A biome with a `wang_template_file` gets a
   herringbone wang map; a procedural biome with `<BitmapCaves>` gets one carved out of noise;
   a procedural biome with a `bitmap_noise_file` gets that image as its map; a biome with none
   of these gets a shared 1 x 1 dummy map. Log lines `"Wang offset: "` and
   `"<Biome> - <area>: <n>"` bracket each one. This is per *biome region*, not per chunk, and it
   is the expensive part of loading.
6. **Load the pixel-scene tables** (`0x0087edd0`): `data/biome/_pixel_scenes.xml` (a
   `<PixelScenes>` of `<PixelSceneFiles>`), and the biome-relative tables in
   `data/biome_impl/`.
7. Optional debug dumps: `temptemp/_biomes_all_wang.png` and `temptemp/_biomes_all_wang2.png`.

## Phase 2: per chunk, on demand

A chunk is generated the first time anything needs it. The driver is the streaming system
(`0x007422c0`, which owns `??SAV/world/.stream_info`, `world_sim.bin`, `world_tree.bin` and
`world_pixel_scenes.bin`); it hands work to `0x007420f0`, which loops
`0x0073d6a0` while jobs remain and then saves each generated chunk.

Generation is **two functions**, and this split is the single most useful thing to know:

| function | role |
|---|---|
| `0x0073b040` | the **per-pixel** pass. Calls `ProceduralTerrain::GetMaterialAt` for all 262144 cells and writes each material or allocates each heap cell. Fills the decor, background, pixel-sprite and ore/spawn lists. Ends by building the 128 x 128 coarse grid and setting `chunk+0xC8 = 1`. Runs on a worker thread. |
| `0x0073c440` | the **per-object** pass (`IMPL_CreateNewChunk_PART2`). Physics bodies, decor, trees, backgrounds, sprites, the biome's Lua `init`, and the Lua spawn calls for every ore record. |

`0x0073b040` is the only function in the whole binary that calls `GetMaterialAt`
(`0x0087d0e0`); `0x0073c440` never does. The two run in order because `PART2` consumes the
lists `0x0073b040` filled.

### Ordered steps

| # | step | function |
|---|---|---|
| 1 | short-circuit if the chunk has a `world_<x>_<y>.png_petri` save cache | inline |
| 2 | allocate and zero the 1 MiB cell table | `0x0073c220` |
| 3 | `Allocate64x64` - create the 64 chunk-blocks | `0x00729470` |
| 4 | weather/rain initialiser for this chunk | `0x006f31e0` |
| 5 | queue the per-pixel worker on the thread pool | lambda at `0x0073c220` |
| 6 | **per pixel:** resolve biome, compute material, write it | `0x0073b040` -> `0x0087d0e0` -> `0x007048c0` |
| 7 | air pixels inherit a neighbouring background/vegetation item | `0x00704a30` |
| 8 | append trees/decor to the chunk's `+0x80` list | `0x008a8040` |
| 9 | append backgrounds to `+0x8C` | inline |
| 10 | collect ore/spawn requests over the chunk rect | `0x0087d380` |
| 11 | re-assign objects between the 3x3 neighbouring chunks | `0x00721870` |
| 12 | build the 128 x 128 coarse grid | `0x0073af60` |
| 13 | mark the chunk finished (`chunk+0xC8 = 1`, under a lock) | inline |
| 14 | insert the coarse grid into the coarse map | `0x00861da0` |
| 15 | Box2D bodies for the chunk's objects | `0x0073eed0` (`PART1`) |
| 16 | decor loop | `0x0087d7e0` |
| 17 | tree loop -> `BiomeMaterials::InsertTree` | `0x0087d670`, `0x0089e010` / `0x0086ef30` |
| 18 | background loop | `0x0086f030` |
| 19 | pixel-sprite loop | `0x0087d730`, `0x0086f3c0` |
| 20 | 3x3-neighbour object re-assignment | `0x00721da0` |
| 21 | call the biome's Lua `init(x0, y0, 512, 512, 0)` | `0x0078cfb0` + `0x0078c270` |
| 22 | ore/spawn loop -> one Lua call per record | `0x0065dd70` + `0x0078ce40` |
| 23 | finalise and tear down | `0x006342e0`, `0x00739880` |
| 24 | end of batch: prune the tree list, place pixel scenes | `0x0087ec40` -> `0x00882dd0` -> `0x00880fb0` |

Steps 6-13 and 15-23 are the two functions; step 24 is `0x0087ec40`, which `0x0073d6a0` calls
once per batch.

### Two cell representations

A pixel's material ends up in one of two places, decided by `CellMaterial + 0x38`, the cell
type:

- **type 3** - written as a flat `uint32` material value at `table[(y-y0)*512 + (x-x0)]`.
- **types 1, 2, 4** - a heap cell object is allocated (0x40, 0x3C and 0x28 bytes respectively)
  and the pointer stored in the parallel grid at `(row << 9) | col`.

`GridWorld::CreateCell` (`0x007048c0`) has **no case for type 3** and returns 0, which is
exactly why the writer special-cases it. Type 3 is the one cell type that is not an object.
The names of types 1, 2 and 4 are not recovered here.

## What is *not* a parameter

Worth stating, because it is the usual assumption and it is wrong:

- There is no "world size" parameter. 70 x 48 comes from `data/scripts/biome_map.lua`, which
  *is* replaceable.
- There is no global cave-density parameter. Caves are per-biome (`<BitmapCaves>` inside
  `data/biome/NAME.xml`) or come from the wang template image.
- There is no ore-frequency parameter. Ore density is the set of `<MaterialComponent>` value
  ranges plus their perlin/polka gates.
- The seed is a single `int32` and nothing else. There is no second "shape seed"; the wang
  offset and the per-chunk RNG are derived from it.

The only `magic_numbers.xml` entries that touch world generation are listed below; "shipped value" is what the retail file sets, and a key it leaves out keeps its compiled-in default:

| key | shipped value | what it does |
|---|---|---|
| `BIOME_MAP` | `data/scripts/biome_map.lua` | the map script to run |
| `BIOME_PATH_FIND_HEIGHT_LIMIT` | `205` | vertical limit for biome pathfinding |
| `BIOME_PATH_FIND_WORLD_POS_MIN_X` / `_MAX_X` | not set (compiled-in `159` / `223`) | horizontal limits for biome pathfinding |
| `BIOME_APPARITION_CHANCE` | `30` | chance of a biome apparition |
| `BIOME_RANDOM_BLOCK_CHANCE` | - | chance of a random blocked-off biome region |
| `BIOME_USE_BIG_WANG` | - | use the large wang map variant |
| `NUM_ORBS_TOTAL` | `12` | how many orbs the world contains |
| `WORLD_SEED` | - | seed, if not set through Lua |
| `STREAMING_ENABLED`, `STREAMING_FREQUENCY`, `STREAMING_CHUNK_TARGET` (12), `STREAMING_PERSISTENT_WORLD`, `STREAMING_AUTOSAVE_PERIOD_SECONDS` | | how eagerly chunks are generated and saved |

## Failure modes you can hit by editing the data

| symptom | cause |
|---|---|
| `Biome load error - couldn't find biome for color: <rrggbb>` | a map pixel whose colour is not in `_biomes_all.xml` |
| `Biome - couldn't find a biome at: <x>, <y>` | the chunk's map pixel resolved to no biome (its colour was not in `_biomes_all.xml`). The coordinates printed are the chunk's centre. X wraps around the map width and Y is clamped to the first and last row, so a position outside the 70 x 48 window still resolves to a map pixel |
| `Warning - biome: <name> - doesn't have lua file...` | `biome+0x1D8` is empty, so the ore/spawn loop has nothing to call. Set `lua_script` on the `<Topology>`. |
| a biome that generates but is full of air | `type="BIOME_WANG_TILE"` with a `wang_template_file` that is mostly white: white writes only the density weight, so no tile is emitted and the per-pixel x threshold rejects everything. Or `wang_map_width`/`height` too small for the template |
| ore that ignores its XML position in the list | expected: `material_index` is the sort key, and lower wins |
| nothing spawns where the wang image says it should | the colour must be known to the spawn dispatcher: either registered by the biome's own `RegisterSpawnFunction` call or listed in `data/scripts/wang_scripts.csv`. How the two are combined is not recovered - see [worldgen-wang.md](worldgen-wang.md) |

## What is not recovered

- `FossilComponent`'s third field is `seed` (default `1`) and its `material` default is `bone` -
  both read straight out of the executable.
- `add_perlin_scale_y` is parsed from XML and never read by the material selector: the perlin it
  feeds is called with a literal `0` as its second argument.
